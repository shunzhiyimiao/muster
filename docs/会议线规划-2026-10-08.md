# 会议线规划(2026-10-08)

> 2026-10-08 决定:**做真实的语音会议室与视频会议室**。总体规划 §1.2 非目标第一条("语音和视频会议第一版不做")自本日起撤销;
> 会议线纳入正式范围。现状盘点与方案见本文;实现进度见 docs/README.md 的对照表。

## 边界(不可放开)

1. **转写只走本地 provider**(服务端架构 边界五):云端 STT 一律 fail-closed 拒绝,演习同样拦。
2. **restricted 会议禁录**:入会令牌里 `can_record = false`,任何录制能力都不得绕过。
3. **会议需要服务端**:单机模式没有可以开会的对象,界面只放实话卡,不放概念稿。
4. 会议与团队频道的关系:会议从属于频道,继承频道密级;密级只升不降。

## 一个会议室实体,两种模式

`mode = voice | video`。语音室只开音频,轻、省带宽、隐私好;视频室在此之上加摄像头与屏幕共享。
两者共用:入会令牌与权限判定、密级、转写 Agent、行动项、审计。主持人可在语音室里临时开视频,反过来不行。

## 现状(2026-10-08 盘点)

- 语音端到端通:桌面壳与网页端(livekit-client 2.21)推麦收音;参会者列表与说话人高亮为真;Agent 独立账号入会,本地 whisper 转写,被 @ 到文字作答,散会提炼行动项。有记录的验证只有 1 真人 + 1 Agent。
- 视频半成品:桌面壳能开摄像头,网页端只能收;没有屏幕共享、设备选择、真静音(现为停推)、录制、TTS。
- 缺口:桌面壳进会不拉历史纪要;行动项 4 秒轮询;Agent daemon 5 秒轮询且单进程;**会议不进审计链**;侧栏"进行中"写死;服务端会议接口没有端到端测试。
- 基础设施已就位:LiveKit(7880/7881/7882udp)、faster-whisper(:9000)、PostgreSQL、muster-server;生产部署有 TURN(仅 UDP 3478)与 TLS。

## 进度

**2026-10-08 阶段 1 代码部分完成**(同日三个提交:桌面壳与网页端 / 服务端与审计 / Agent 守护进程):

- 桌面壳:进会先拉 `GET /meetings/:id/transcript` 补历史,再收 SSE 增量(按 ts+speaker+text 去重);行动项改为服务端 SSE `action_item` 推送,进会拉一次全量后按 id 合并,不再 4 秒轮询;侧栏徽标改为真实的「N 场进行中」(各远端频道汇总,收到 `meeting` 推送即重拉);大厅有「结束」按钮、显示「Agent」标;会议被别人结束时会议室页出横幅并断开;离开时调 `POST /meetings/:id/leave`。
- 媒体:麦克风/摄像头开关状态**只读 SDK**不另存;关麦即停底层音轨(系统指示灯灭);开麦前 `permissions.query` 预检,getUserMedia 失败按错误名给出 macOS 放行指引;设备面板可选麦克风/摄像头,扬声器仅在 webview 支持 `setSinkId` 时可选(否则如实标注跟随系统);**共享屏幕按钮按 `getDisplayMedia` 是否存在决定可用**,支持则最小接线(焦点区并排显示)——这就是「先做的试验」,结论看真机上按钮是否可用。
- 服务端:`meeting.start / join / leave / end / transcript(每行只记哈希)/ level.raise / agent` 七种事件进服务端审计链(muster-audit 新变体),**先记账再动库**;`Push::Meeting`(started / ended / agent / level)推给所有在线端;新增 `POST /meetings/:mid/leave`;结束幂等并补齐所有参会者的 left_ms;散会后不再收纪要、不再入会;`tests/meetings_e2e.rs` 四个端到端测试(生命周期与链上无正文、SSE 推送、外人被拒、密级只升不降且 restricted 禁录),需 `DATABASE_URL` 指向活的 PostgreSQL。
- Agent 守护进程:订服务端 SSE,`meeting` 事件一到立刻对账(通常 1 秒内入会),30 秒兜底轮询;会议结束 / 被请离时叫停该会的任务——退出房间、做散会提炼、再结束(此前 Agent 自己是参会者,房间永不空,散会提炼实际只有 Ctrl-C 触发);令牌过期(12 小时)自动重登(此前过期后静默失败两周)。

阶段 1 仍欠:**2 真人 + Agent 按《多人会议测试计划》实测并出结论**(需要两台机器与用户参与);掉线不记 leave(只有客户端主动离开才记,LiveKit webhook 未接)。

## 先做的试验

Tauri 的 WKWebView 能否 `getDisplayMedia` 屏幕共享。不行则屏幕共享走 Rust 侧原生采集(ScreenCaptureKit)+ LiveKit Rust SDK 推流,成本高一个量级。阶段 2 开工前先定。

## 风险

- 本地转写的 CPU 天花板:CPU 上 base 模型是上限,small 慢 9 倍;多人同时说话丢帧(队列 ≈ 5 秒)。
- 网络:公网只有 UDP TURN,纯 UDP 被封的网络进不来;浏览器端在 http 内网地址下开麦被拦,必须 TLS。
- 同一账号两端入会会被 LiveKit 互踢(DuplicateIdentity),Agent 必须独立账号。
- Agent 的 livekit Rust SDK 钉在 git commit,构建期要拉 100MB+ 预编译 WebRTC;内网部署要预缓存。
