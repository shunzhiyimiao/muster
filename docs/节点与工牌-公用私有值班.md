## 节点与工牌:公用 Agent、私有 Agent、值班 Agent(2026-10-25 定)

> 放在 `docs/服务端架构.md` 第 1 节「部署拓扑」之后。它把 P2-09(Runner Service Account)、
> 边界三(节点注册公钥并锚定)和会议 Agent 的部署问题收成同一个实体:**节点**。

### 两条已定的产品决定

1. **私有 Agent 不进频道。** 公用 Agent(值班)把事派给**团队成员本人**,
   成员自己决定交给哪个私有 Agent 去做。会议记录分发、任务分发都走这条路。
2. **值班 Agent 只提案,不执行。** 必须由**被派到的那个人**收到、并亲手确认,
   才会有任何东西开始跑。

### 三种工牌

| | 公用 Agent | 值班 Agent | 私有 Agent |
|---|---|---|---|
| 是什么 | 组织的工牌 | 组织设置里指定的**一张**公用工牌 | 个人给自己建的工牌 |
| 谁建 / 谁管 | 管理员 | 管理员指定 | 本人 |
| 住在哪个节点 | 组织节点(常开;默认是服务器本机那个) | 组织节点,且必须有本地转写能力(边界五) | 本人的节点(桌面壳兼任) |
| 定义存在哪 | 服务端下发(与 provider 目录同一机制) | 同左 | 本机 `~/.muster/roster/`,**不上传**,服务端只登记哈希 |
| 模型密钥 | 组织节点上的 | 同左 | 本人节点上的 |
| 进频道 | 能 | 能(要听会、要在频道发纪要) | **不能** |
| 工具档位 | 按岗位卡 | **只读 + 提案**:不写文件、不跑命令 | 按岗位卡(在本人 worktree 里) |
| 审计链 | 组织节点的链 | 组织节点的链 | 本人节点的链,锚定到服务端 |

**为什么"住在组织节点"而不是"住在管理员电脑上":** 管理员一合盖,会议记录和派活就全停——
这正是 2026-10-19 会议 Agent 跑在开发机上时的状态。管理员是**管它的人**,不是**它的宿主**。

**为什么值班 Agent 的执行面要最小:** 它的可见面是全组织最大的(所有会议、任务、名册)。
看得多的不动手,动手的只看自己那一块。它被一句会议发言带偏,最坏结果是一条被驳回的提案,
不是一次跑错的改动。

### 派发:从提案到私有 Agent 执行

```mermaid
sequenceDiagram
    participant V as 值班 Agent<br/>(组织节点)
    participant S as 服务端
    participant M as 成员本人<br/>(桌面壳)
    participant P as 成员的私有 Agent<br/>(本人节点)

    V->>S: 提案 dispatch(内容 · 出处原话 · 建议负责人 · 密级)
    S->>M: 投进本人收件箱
    M->>S: 接受(自己做 / 交给私有 Agent X) 或 驳回(附理由)
    Note over S: 只认被派到的本人;<br/>先落 approval.decision 再动库
    S-->>P: 下发给本人节点(仅当选择了私有 Agent)
    P->>P: 在本人 worktree 里跑,本人节点的链记账
    P-->>M: 结果只回给本人
    M->>S: 本人决定:标完成 / 把结果发回任务或频道
```

状态机(由 `meeting_action_item` 推广而来):

```
proposed ──本人接受──▶ accepted(self)       ──本人标完成──▶ done
    │                 accepted(private:X) ──节点回填 run_id──▶ running ──▶ result_ready ──本人──▶ done
    ├──本人驳回──▶ rejected(附理由,回到值班 Agent 的视野,可重提或由人直接指派)
    └──超时未处理──▶ expired(提醒过后回收,不自动转派)
```

### 闸(每条都要有测试,照会议线"四条闸,真机验过"的标准)

1. **只有被派到的本人能接受或驳回。** 值班 Agent 不能确认自己的提案(已有);
   管理员、会议主持人也不能替本人接受——派活是请求,不是命令。
2. **`owner_hint` 永远不作授权依据**(已有)。值班 Agent 把它解析成具体账号写进 `assignee`,
   解析错了的后果是"错的人收到一条可以驳回的提案",不是"错的人的电脑开始跑"。
3. **私有 Agent 只接本人接受过的派发。** 节点拉取任务时,服务端核对节点归属人 == `assignee`。
4. **密级跟着任务走,在本人节点上照样 fail-closed。** 派发单带着来源的密级(会议 / 频道 / 仓库取高);
   本人选私有 Agent 时,界面先按**该节点下发到的 provider 目录**判断它落不落得下——
   受限级任务而该节点只有云端 provider ⇒ 这个选项不可选,只能"自己做"。
   真跑起来时会话棘轮从这个密级起步,不从 public 起步。
5. **私有 Agent 的产出不自己进频道。** 结果只回本人;发回任务或频道是**本人的动作**,
   以本人身份发出,标"由私有 Agent 协助"。人是私有世界和共享世界之间的唯一一层膜。
6. **每一步都进审计链,正文只留哈希:** 提案(组织节点链)、接受 / 驳回(服务端链,`approval.decision`)、
   执行(本人节点链),三条链靠派发单 id 和内容哈希串起来,锚定后组织侧可查。

### 会议记录分发:投递不是执行

散会后值班 Agent 产出两样东西,**处理方式不同**:

- **纪要本身**:按会议的可见范围投给与会者(受限级会议只投给有权限的人)。这是信息投递,
  不在任何人的机器上执行任何东西,**不需要逐人确认**。现在"回顾落 `/summary` 并发频道消息"不变。
- **从纪要里提炼的行动项**:每一条都是一张派发单,走上面的流程。

成员收到纪要后,想让私有 Agent 帮忙(比如据此起草后续邮件),那是他本地的动作,不经值班 Agent。

### 数据模型变更

```sql
-- 节点:一台登记到组织的机器。公钥既用于鉴权,也用于签审计锚点(边界三),P2-09 的 mTLS 可省
node(id, org, name, owner_account NULL /* NULL = 组织节点 */, pubkey, capabilities JSONB,
     version, last_seen_ms, created_ms)

-- 工牌加三列
badge.scope     -- 'public' | 'private'
badge.owner     -- 私有工牌的主人;公用为 NULL
badge.node_id   -- 住在哪个节点

-- 组织设置
org.duty_badge  -- 值班 Agent;必须 scope='public' 且所在节点 capabilities 含本地转写

-- meeting_action_item 推广为 dispatch(或加列,保留旧表名)
dispatch(id, source_kind /* meeting | channel | task */, source_id, text, source_quote,
         owner_hint, assignee, sensitivity, proposed_by,
         status /* proposed|accepted|running|result_ready|done|rejected|expired */,
         accepted_mode /* self | private */, delegate_badge, run_id, result_hash,
         decided_ms, created_ms)
```

### 接口草案

| 接口 | 谁调 | 说明 |
|---|---|---|
| `POST /nodes/enroll` → `POST /nodes/enroll/:code/approve` | 节点 / 管理员 | 设备码入网:节点本地生成 ed25519,管理员在网页确认,服务端存公钥 |
| `GET /nodes/:id/desired` + SSE | 节点 | 设定值:我该托管哪些工牌、该进哪些会、有哪些已接受的派发 |
| `POST /nodes/:id/heartbeat` | 节点 | 反馈:实际状态 + 能力;断联超时 ⇒ 其上工牌标"不可用" |
| `POST /dispatch` | 值班 Agent | 提案(只能是 proposed) |
| `GET /me/inbox` | 成员 | 收件箱 |
| `POST /dispatch/:id/decide` | 成员本人 | `{accept: self \| private:<badge>}` 或 `{reject, reason}` |
| `POST /dispatch/:id/run` | 本人节点 | 回填 run_id(核对节点归属人 == assignee) |
| `POST /dispatch/:id/result` | 本人节点 | 只交结果哈希,正文留在本人节点 |

### 诚实边界 / 未决

- **主人离线 = 私有 Agent 离线。** 不做自动转派:那会把"在谁的机器上、用谁的密钥"变得不可审计。
  超时只回收、提醒,由人重新指派。
- **值班 Agent 选人靠名册岗位卡和历史**,会选错。闸 1、2 保证选错的代价是一次驳回。
- **超时时长**、**一个组织能否按团队设多个值班 Agent**:未定,第一版一个组织一个。
- **私有 Agent 永远不进频道**是产品决定,不是技术限制;将来要放开,闸 4、5 已经覆盖了必要的约束。

### 实施顺序

1. **组织节点 + 值班 Agent**:`node` 表、设备码入网、会议 daemon 改用节点密钥 + `org.duty_badge`
   (替掉 compose 里写死的 A-007 口令);`to-server.sh` 默认在服务器本机装一个节点。
   ——这一步直接解决会议 Agent 的部署问题。
2. **派发单**:`meeting_action_item` → `dispatch`,确认权收窄到 `assignee` 本人,桌面壳收件箱。
3. **私有 Agent**:桌面壳以本人节点身份入网,`badge.scope/owner`,"交给私有 Agent"选项与闸 3、4、5。
